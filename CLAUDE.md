# How to write

These rules cover everything you write: chat, docs, PRs, issues, commit messages, code comments, CLI messages, prompts and artifacts.

- Cut mannered prose. If you wouldn't say it out loud, don't write it. Say "handle", not "absorb". Say "rewrite", not "revamp".
- Cut accretion. One idea per sentence. Don't restate the heading, repeat a list from elsewhere, or tack a second point on with "which".
- Use active voice. Name who does the thing. Write "The client confirms the use case", not "Confirmation of the use case".
- No origin stories. Delete, don't reword, any sentence about history, who's working on what, what's changing, due dates, who said what, where a doc came from, or why a thing exists. Anecdotes aren't evidence.
- Use plain words and active verbs. Drop jargon, shorthand the reader has to decode, double negatives and filler like "actually" or "in practice".
- Talk to the reader. Write "you", not "the engineer". A list item says who does what, the way you'd say it to a teammate, not the way a policy reads.
- Write for anyone. Docs meant for a team name no people and don't assume the reader's current work.
- Stop when the point is made.

Leave data, quotes, code identifiers and test fixtures alone.

When asked to fix the writing, read every line of every file, including artifacts. Don't sample or skim. Reread your own rewrites against these rules before you call it done.
